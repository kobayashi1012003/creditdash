# CreditDash

A dashboard where someone saves the credit cards they own and sees which card
to use, what credits are left, and whether each annual fee pays for itself.

## Product principles

Apply these on every screen.

1. Answer "which card should I use?" in one tap.
2. No ads, no pop-ups, no walls of text. If a sentence is not needed, cut it.
3. Everything is entered manually. Never link a bank, ever.
4. Never collect card numbers, expiry dates, CVVs or account logins.
5. No fixed running costs at launch.

## Stack

Next.js 16 App Router, TypeScript, Tailwind v4, Motion, Recharts, Phosphor
icons, next-themes. Deployed to Cloudflare Workers through the OpenNext
adapter.

- **Node runtime only.** Never `export const runtime = "edge"`. OpenNext
  requires it.
- **`cacheComponents` is off** in `next.config.ts`. It hangs the Workers
  runtime. The comment there explains why; do not turn it back on without
  re-testing `npm run preview`.
- **Next 16 has breaking changes** from earlier versions. Check
  `node_modules/next/dist/docs/` before reaching for a remembered API.
- **Verify a dependency exists** in `package.json` before importing it.

## The data layer

**Nothing outside `lib/data/` touches storage.** Pages and components call the
hooks and functions in `lib/data/index.ts` and know nothing about where the
data lives.

- `schema.ts` is the persisted shape, versioned, mirroring the tables in
  `creditdash-plan.md` section 6 so each key maps to a Supabase table later.
  It validates whatever it reads rather than casting: storage can hold a
  half-written object or something typed into devtools, and a crash on load
  would lock someone out of their own wallet.
- `store.ts` is the browser-storage backing. Phase 6 replaces its body with
  Supabase calls and nothing else changes.
- `index.ts` is the public API.

**Writes are async** (`await addCard(id)`) even though localStorage is
synchronous. Supabase will not be, and every call site already awaiting is
what makes Phase 6 a change inside one directory instead of across the app.
Do not "simplify" these to synchronous.

**Reads are hooks** over `useSyncExternalStore`, so a change in one component
or one browser tab reaches every other. `useIsLoading()` is true until storage
has been read; the server cannot know what is stored, so first paint is a
skeleton rather than a guess that then gets replaced.

## Credit resets

`lib/credits/reset.ts` owns when a credit resets, and it is the piece of this
product most worth being correct: getting it wrong tells someone a credit is
still available after it has reset, or that they have lost one they still
have.

Issuers use two bases. A calendar credit's year runs January to December. An
anniversary credit's year runs from the month the card was opened, so a card
opened in November has quarters starting in November, February, May and
August. Never assume January.

The module is deliberately dependency-free, with no imports and no path
aliases, so `node --test` can run its tests directly with Node's native
TypeScript support. Keep it that way; the period model (`CreditPeriod`,
`ResetBasis`, `PERIOD_COUNT`) lives there and `data/types.ts` re-exports it.

Storage keys come from this module. Calendar windows use the plain format
(`2026`, `2026-H1`, `2026-Q2`, `2026-03`); anniversary windows carry their
cycle start (`a2025-11`, `a2025-11:Q2`), because "the second quarter" is a
different three months depending on when the card was opened. Changing a key
format means a schema version and a migration, never an edit in place.

## Calculator and ranking maths

`lib/calculators/engine.ts` holds every number the app states about what a
card is worth: earn rates, caps, break-even, spend value and the "which card"
ranking. Like the reset logic it has no runtime imports (its type imports are
erased), so `node --test` runs its tests directly.

Three rules it exists to enforce:

- **Rank on value, never on the multiplier.** 12x Hilton points at 0.5 cents
  is worth less than 4x Membership Rewards at 1.9. A multiplier-only ranking
  gives the wrong answer confidently, which is worse than no answer.
- **Respect the caps.** Amex Gold earns 4x on groceries to $25,000 a year and
  1x after. Multiplying straight through overstates a $36,000 spender by
  33,000 points. Spend past a cap falls to the card's everything-else rate,
  and a capped everything-else rate falls to 1x.
- **Use the user's valuations, not the seed defaults.** Settings says these
  drive every dollar figure in the app, so they have to. Signed-in surfaces
  read `useValuations()`; the public landing page has no user and uses
  `DEFAULT_VALUATION_MAP`.

## Card art

Drop a file named after the card id into `public/cards/` and `CardFace` picks
it up. `scripts/build-card-art-manifest.mjs` runs before dev, build and
typecheck, and writes `data/card-art.generated.ts` listing what is actually
there.

The manifest exists because the alternative is requesting
`/cards/<id>.webp` and waiting for a 404 to learn the file is missing, which
paints a blank card for a frame and puts a failed request on the wire for
every card. Most cards have no art, so that is the normal case. `onError`
still falls back, for a file removed between a build and a request.

### Client and server boundaries

Plain data exported from a `"use client"` module does not survive into a
server component. The calculator registry is split into
`components/calculators/registry.ts` for exactly this reason; keep data and
client components in separate files when a server page needs the data.

### Hooks

Never write state from an effect to read an external value. Use
`useSyncExternalStore`: `lib/use-media-query.ts` for breakpoints and
`lib/use-stored-flag.ts` for remembered booleans. The lint rule enforces it.

## Design tokens

`app/globals.css` is the single source of truth. **Nothing outside that file
hardcodes a colour, radius, duration or easing curve.** Changing the brand means
editing that one file.

### Colour

| Token | Light | Dark |
|---|---|---|
| `--cd-bg` | `#FAFAF9` | `#0B0B0C` |
| `--cd-surface` | `#FFFFFF` | `#151517` |
| `--cd-text` | `#0B0B0C` | `#F5F5F4` |
| `--cd-text-muted` | `#6B6B70` | `#9A9AA0` |
| `--cd-border` | `#ECECEA` | `#232326` |

Five pastels: mint, lavender, peach, sky, butter. Each has a `-ink` companion
that is legible on it. In light mode the pastel is the fill and the ink is a
deep hue-matched tone. In dark mode that inverts: the fill is a deep tint of the
surface and the ink carries the colour. A literal 20% alpha pastel on `#151517`
would leave chip text under AA, which is why dark is not just the light value
with opacity.

Every pairing is verified at WCAG AA or better in both themes. Re-verify if you
change one.

A spend category owns one pastel and keeps it on every screen. The mapping
lives in `lib/categories.ts` and nowhere else. Eight categories share five
pastels along family lines; "everything else" is deliberately uncoloured so the
coloured categories keep their meaning.

### Shape

One radius scale, applied consistently: containers `rounded-widget` (24px),
inputs, inner surfaces and card faces `rounded-inner` (16px), buttons, chips
and category selectors `rounded-pill` (999px). Buttons are pills, matching the
chips. Nothing picks a radius outside this scale.

Elevation is one soft layer tinted to the background. Grouping comes from
borders and spacing before it comes from shadow.

### Type

`--font-sans` is Geist, `--font-display` is Newsreader. Both load through
`next/font`, never a `<link>`. Swap either by changing the token.

Instrument Serif and Fraunces are banned: they are the two most recognisable
generated-site display serifs. (This is a deliberate change from
`creditdash-plan.md` section 3.4, agreed with the owner.)

Numbers are tabular by default so balances line up in a column.

### Motion

Curves and durations are tokens. Pick by element type:

| Element | Duration | Curve |
|---|---|---|
| Button press | `--cd-dur-press` 140ms | `ease-out` |
| Hover, colour change | `--cd-dur-hover` 180ms | `ease-out` |
| Tooltip, small popover | `--cd-dur-pop` 200ms | `ease-out` |
| Dropdown, select | `--cd-dur-menu` 220ms | `ease-out` |
| Drawer, calculator panel | `--cd-dur-panel` 280ms | `ease-drawer` |

Rules:

- **Never `ease-in` on UI.** It delays the first frame, which is the moment the
  user is watching most closely, so it reads as sluggish.
- **Never `transition: all`.** Name the properties.
- **Animate only `transform` and `opacity`.** Never `width`, `height`, `top`,
  `left`.
- **Never animate from `scale(0)`.** Start at `scale(0.95)` with `opacity: 0`.
  Nothing in the real world appears from nothing.
- **Every pressable element gets `active:scale-[0.97]`.**
- **Popovers scale from their trigger**, not from centre. Modals are the
  exception and stay centred.
- **Motion's `x`/`y` shorthand props are not hardware accelerated.** They run on
  the main thread and drop frames under load. Use a full `transform` string.
- **Prefer CSS transitions over keyframes** for anything that can be retriggered
  rapidly. Transitions retarget mid-flight; keyframes restart from zero.
- **Never `window.addEventListener('scroll')`.** Use Motion's `useScroll`, an
  `IntersectionObserver`, or CSS scroll-driven animation.
- **Nothing routine runs over 300ms.**
- Import from `motion/react`, not `framer-motion`.
- Isolate motion in `'use client'` leaf components. Layouts stay server
  components.

`prefers-reduced-motion` is handled globally in `globals.css`. Reduced motion
means gentler motion, not none: opacity and colour still carry meaning,
movement does not. Anything with its own JS-driven motion must also check
`useReducedMotion()`.

## Writing the interface

### Rules that produce a generated-looking site, so are banned

- **Zero em dashes (`—`) and zero en dashes (`–`) in any visible string.**
  Headlines, labels, body, buttons, captions, alt text, error messages. Use a
  comma, a period, parentheses, or a plain hyphen. This is the single most
  recognisable tell.
- No purple or blue gradient hero, no gradient text, no glowing blobs.
- No filler verbs: "Unlock the power of", "Elevate your", "Seamless",
  "Revolutionize", "Next-gen".
- No emoji as icons. Use Phosphor glyphs.
- No three identical feature cards in a row with an icon on top.
- No uppercase wide-tracking eyebrow label above every section. At most one per
  three sections.
- No section numbering (`01 / INDEX`, `002 · Capabilities`).
- No scroll cues ("Scroll to explore").
- No decorative status dots unless the dot means a real state.
- No fake product screenshots built from `<div>`s.
- No placeholder text. Sample data is specific and real-feeling: actual card
  names, real amounts, real dates. Never "Lorem ipsum" or "$XX.XX".
- No generic names or brands ("John Doe", "Acme").
- Do not centre everything. Layouts are deliberate and slightly asymmetric.
- No default shadcn look. Restyle every component to the tokens.

### Copy

Plain, active, sentence case. Name things the way a user would. A button says
what happens: "Save changes", not "Submit". The same action keeps the same name
through a whole flow, so a "Publish" button produces a "Published" toast.

Errors explain what went wrong and how to fix it, without apologising and
without being vague. An empty screen is an invitation to act, not a mood.

Re-read every visible string before calling a screen done. If a phrase is cute
but does not quite make sense, replace it with a plain one.

### Quality floor

Every screen, every time:

- Works at 375px and at desktop width, with no horizontal scroll. Measure it
  (`scrollWidth - clientWidth`) rather than eyeballing; 35px of drift is
  invisible in a screenshot and real on a phone.
- **`sr-only` inside a horizontal scroller needs a positioned ancestor.** It
  is `position: absolute`, so without one its containing block is `<body>`,
  it lands at the scroller's unclipped coordinates, and it widens the whole
  page. `overflow: hidden` does not clip it, which is why this hides well.
  Add `relative` to the cell or wrapper.
- **A flex item will not shrink below its content unless you let it.** Five
  tab bar items with `flex-1` needed 410px on a 375px phone. `min-w-0` plus
  a truncating label is the fix.
- Every interactive element has hover, press, focus and disabled states.
- Focus is visible and never removed. The treatment is global in `globals.css`.
- Light and dark both checked. Never ship a screen seen in one mode only.
- Empty, loading and error states exist. Loading is a skeleton shaped like the
  real content, not a spinner.
- One clear focal point per screen, with type size and weight doing the work.

## Data and privacy

- Never store or request card numbers, expiry dates, CVVs or bank logins. There
  is no field for them anywhere.
- All data access goes through `lib/data/`. Pages never touch storage directly.
  Phase 6 swaps browser storage for Supabase by changing that layer only.
- Every premium check goes through one `hasFeature` helper against one limits
  config, so a feature can move between Free and Premium in one edit.
- Secrets live in environment variables and never in the repo. `.env.example`
  carries names only.

## Deviations from creditdash-plan.md

Agreed with the owner. Keeping the list here so later phases do not "fix" them
back.

| Plan says | Built as | Why |
|---|---|---|
| Instrument Serif (3.4) | Newsreader | Instrument Serif is one of the two most recognisable generated-site display serifs, which fights the plan's own anti-generic goal in 3.2 |
| Lucide icons (8) | Phosphor | Lucide is the default icon set in generated UI; Phosphor has weights and better finance glyphs |
| Dark pastels at 20% opacity (3.3) | Opaque hue-matched dark tints | 20% alpha on `#151517` puts chip text below WCAG AA |
| GitHub push in Phase 5 | Pushed in Phase 0 | Owner asked for the repo from the start. Connecting Cloudflare to the repo still happens in Phase 5 |
| shadcn/ui (8) | shadcn/ui on Base UI primitives | The generator's Base UI target gives the same components over better-maintained primitives, and `pick-ui-library` independently recommends Base UI. Tokens are remapped onto ours so nothing ships in default styling |
| Seed file in Phase 2 | Written in Phase 1 | Phase 1 needs sample data on every page; writing it twice would be waste. Phase 2 still owns `lib/data/` and persistence |
| Tracker and Settings persistence in Phase 3 | Done in Phase 2 | Once the store existed, leaving those screens on local state would have been two sources of truth. Phase 3 still owns reset logic and its tests |
| No test framework named | `node --test`, zero dependencies | Node 26 runs TypeScript directly, so the tests need no runner, no transpiler and no new packages |
