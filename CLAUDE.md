# CreditDash

A dashboard where someone saves the credit cards they own and sees which card
to use, what credits are left, and whether each annual fee pays for itself.

### The domain

- **Porkbun holds the registration only.** Its nameservers point at
  Cloudflare, which answers DNS. Add or change records in Cloudflare.
- **`creditdash.co` and `www.creditdash.co` are Worker custom domains**
  (Worker > Domains & Routes). They own their DNS records; never add an A
  or CNAME for either by hand, or the custom domain detaches.
- **One address everywhere.** Zone rules: Always Use HTTPS on, and a
  Single Redirect sends `https://www.*` to the root with path and query
  kept (301). Cloudflare warns that `www` is not a proxied record; that is
  a false alarm for a Worker custom domain.
- **Sign-in follows the page's own origin** (`window.location.origin`), so
  nothing in code names the domain. What does: Supabase URL Configuration
  (Site URL `https://creditdash.co`; Redirect URLs for `creditdash.co`,
  `localhost:3000` and `localhost:8787`), and the Google OAuth client's
  JavaScript origins. A new host needs adding in both. `metadataBase` in
  `app/layout.tsx` is the only place the domain is written, and only for
  absolute links in page metadata.

## Product principles

Apply these on every screen.

1. Answer "which card should I use?" in one tap.
2. No ads, no pop-ups, no walls of text. If a sentence is not needed, cut it.
3. Everything is entered manually. Never link a bank, ever.
4. Never collect card numbers, expiry dates, CVVs or account logins.
5. No fixed running costs at launch.

## Stack

Next.js 16 App Router, TypeScript, Tailwind v4, Motion, Phosphor
icons, next-themes. Deployed to Cloudflare Workers through the OpenNext
adapter.

- **Node runtime only.** Never `export const runtime = "edge"`. OpenNext
  requires it.
- **`cacheComponents` is off** in `next.config.ts`. It hangs the Workers
  runtime. The comment there explains why; do not turn it back on without
  re-testing `npm run preview`.
- **Prerendered pages are served from a static cache**
  (`open-next.config.ts`: the static-assets incremental cache plus
  `enableCacheInterception`). OpenNext's default cache does nothing, so
  until 4 November 2026 every visit rendered its page again, at 25 to 114ms
  of CPU against the free plan's 10ms, and Cloudflare stopped some of them
  with a 503 (`exceededCpu` in Workers Logs). Keep every page static:
  reading `searchParams`, `cookies()` or `headers()` in a page makes it
  render per request again (`/signin` reads `?error=` in the browser for
  this reason). The cache is read-only, so `revalidate`, `revalidatePath`
  or `"use cache"` need R2 or KV first. Check with `curl -I` under
  `npm run preview`: every page should say `x-opennext-cache: HIT`.
- **Next 16 has breaking changes** from earlier versions. Check
  `node_modules/next/dist/docs/` before reaching for a remembered API.
- **Verify a dependency exists** in `package.json` before importing it.

### Setting up on a new machine

The repository carries the code, the docs and the skill *sources*, but three
things are machine-specific and have to be redone. Do these before starting
work, or Claude will be running without the tooling the conventions below
assume.

```bash
git clone https://github.com/kobayashi1012003/creditdash.git
cd creditdash
npm install
npx impeccable install                        # platform binary and hooks
npx skills@latest add emilkowalski/skills     # see the symlink note below
npm test && npm run build                     # confirm the toolchain works
```

- **Node 22.18 or newer.** The tests run through `node --test` on TypeScript
  directly, with no transpiler. On an older Node the suite fails with a
  syntax error that does not name the real cause. `package.json` pins this in
  `engines`.
- **`.claude/skills/` is not in the repo.** It holds per-machine links into
  `.agents/skills/` (junctions on Windows), so a fresh clone has none until
  the two installers above run.
- **The impeccable binary is gitignored** because it is 17MB and built for one
  platform. Its hooks in `.claude/settings.local.json` are POSIX shell and
  will not run on Windows. `npx impeccable install` rewrites both correctly
  for the machine it runs on, so that file may show as modified afterwards.
  That is expected; commit it if the new machine is now the main one.
- **Browser storage does not travel.** The demo wallet, the theme and the
  calculator panel state live in localStorage. A new machine seeds a fresh
  demo wallet on first load, which is correct, not a fault.
- **`gh auth login`** for pushing.

## The data layer

**Nothing outside `lib/data/` touches storage.** Pages and components call the
hooks and functions in `lib/data/index.ts` and know nothing about where the
data lives.

- `schema.ts` is the persisted shape, versioned, mirroring the tables in
  `creditdash-plan.md` section 6. It validates whatever it reads rather than
  casting: storage can hold a half-written object or something typed into
  devtools, and a crash on load would lock someone out of their own wallet.
- `store.ts` holds the state in one of two modes. **local**: signed out,
  browser storage, read synchronously on the first frame (the demo user).
  **account**: signed in, the account read from Supabase once, then every
  write updates the cache first and the database second. A refused write
  rolls the cache back and raises a notice (`useNotice()`), so the screen
  never claims something the database does not hold.
- `remote.ts` is the Supabase side: loading an account into the same
  `Persisted` shape, and one function per kind of write.
- `supabase.ts` is the browser client. Without the env vars it returns null
  and the app runs as the demo user only (`ACCOUNTS_ENABLED`).
- `index.ts` is the public API. Each write passes `mutate()` both the state
  change and its Supabase counterpart; pages cannot tell which mode they are
  in except through `useAccount()`.

**Writes are async** (`await addCard(id)`) even though localStorage is
synchronous. That is what let Phase 6 add Supabase inside this directory
without touching a page. Do not "simplify" these to synchronous.

**Reads are hooks** over `useSyncExternalStore`, so a change in one component
or one browser tab reaches every other. `useIsLoading()` is true until the
state has been read; the server cannot know it, so first paint is a skeleton
rather than a guess that then gets replaced.

### Accounts

- **The database is the guarantee, not the UI.** Every user table has Row
  Level Security; `profiles.plan`, `stripe_customer_id`, `premium_gift` and
  `is_admin` cannot be written by users at all (column grants), and nor can
  `subscriptions`; the free card limit is
  a trigger. `npm run test:rls` proves all of it against the real project
  with two throwaway users. Run it after any migration.
- **Migrations live in `supabase/migrations/`** and are run once, by hand,
  in the SQL Editor. Never edit one that has run; add a new file.
  `FREE_CARD_LIMIT` is duplicated in the limit trigger; change both.
- **No `proxy.ts`.** Next 16 runs it on Node and OpenNext cannot yet. Nothing
  server-side reads the session except `app/auth/callback/route.ts` (the
  PKCE code exchange for Google and the email link),
  `app/api/account/route.ts` (account deletion) and the billing routes
  under `app/api/billing/` (checkout and portal; the webhook has no user
  and proves itself by Stripe's signature instead). Those are the only
  holders of the secret key, and each acts only on the user its bearer
  token proves. The browser
  client refreshes its own session. A server component that needs the user
  would need a proxy first; avoid needing one.
- **Removing a card deletes its credit history** in both modes, matching the
  database cascade.
- **Keys.** `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
  are public by design and inlined at build, so they live in the committed
  `.env.production`. `SUPABASE_SECRET_KEY` bypasses RLS: runtime secret
  only, never `NEXT_PUBLIC_`, never in chat or the repo.
- **The browser client loads on demand.** `supabase()` returns a promise
  and dynamically imports `@supabase/ssr` (about 70 KB). Signed-out
  visitors never download it; the store loads it only when a session
  cookie exists, and the sign-in page warms it with `prepareSignIn()`. Do
  not import `@supabase/*` at the top of any browser module.

### Billing (Phase 7)

- **Only the webhook grants Premium.** `app/api/billing/webhook` checks
  Stripe's signature on the raw body, then reads the customer's
  subscriptions fresh from Stripe and writes `subscriptions` and
  `profiles.plan` with the secret key (`syncCustomer` in
  `lib/billing/server.ts`). It never trusts an event's own copy, so late,
  repeated or out-of-order events still land on the right plan. Checkout's
  success URL changes nothing by itself.
- **No Stripe SDK.** `fetch` with a form body, in `lib/billing/server.ts`.
  The decisions (signature check, which statuses are Premium, row shape)
  are in `lib/billing/stripe.ts`, dependency-free and unit tested like the
  reset logic. `past_due` keeps Premium while Stripe retries.
- **No price id anywhere.** The server looks the price up by its lookup
  key `creditdash_premium_monthly`, so test and live mode each carry their
  own price. Changing the price means a new Stripe price with that key
  (move the key across), not a code change, plus `PREMIUM_PRICE_MONTHLY`
  in `lib/plan.ts` for the displayed figure.
- **Secrets.** `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are runtime
  Secrets on the Worker, like `SUPABASE_SECRET_KEY`. Test and live mode
  have different keys and different webhook secrets. **Never put sandbox
  keys on the live site:** anyone could pay with Stripe's test card and
  get Premium. With no keys, Upgrade says payments are not switched on.
- **Cancelling happens in Stripe's Customer Portal**, set to cancel at
  the end of the period. Before sending a Premium user there, Settings
  warns in a dialog if cancelling would hide cards (owner's rule).
- **Back on Free, extra cards are hidden, never deleted** (owner, 29
  October 2026). `useWallet()` returns only the first `cardLimit(plan)`
  by sort order, so every screen agrees; `useHiddenCardCount()` drives the
  Wallet's notice; the export uses `useWalletIncludingHidden()`. The
  database trigger still refuses a new card while over the limit.
- **Deleting an account deletes its Stripe customer first**, which cancels
  any subscription at once. If Stripe refuses, the account is kept, so a
  charge is never left running with no account to cancel it from.
- **Gifted Premium** (migration `20261030000000_premium_gift.sql`): the
  owner sets `profiles.premium_gift = true` in the SQL Editor (the
  statement is in the migration's header). A trigger then holds `plan` at
  premium whatever the webhook writes; clearing the flag returns the plan
  to what the `subscriptions` rows say. Users cannot write the flag.
  Settings shows "On the house" and no billing button unless they are
  also paying. Never gift by setting `plan` alone: the next Stripe event
  for someone who has paid before would undo it.
- **A gift does not touch Stripe.** Someone paying when gifted keeps
  being charged until they cancel in the portal (Settings still shows
  them Manage billing) or the owner cancels in the Stripe dashboard.
- **Migrations** `20261029000000_subscriptions.sql` and
  `20261030000000_premium_gift.sql` have both run. Users read their own
  subscription rows only; nobody but the server writes them.

## Credit resets

`lib/credits/reset.ts` owns when a credit resets, and it is the piece of this
product most worth being correct: getting it wrong tells someone a credit is
still available after it has reset, or that they have lost one they still
have.

Issuers use two bases. A calendar credit's year runs January to December. An
anniversary credit's year runs from the month the card was opened, so a card
opened in November has quarters starting in November, February, May and
August. Never assume January.

The module is deliberately dependency-free, with no imports and no path
aliases, so `node --test` can run its tests directly with Node's native
TypeScript support. Keep it that way; the period model (`CreditPeriod`,
`ResetBasis`, `PERIOD_COUNT`) lives there and `data/types.ts` re-exports it.

Storage keys come from this module. Calendar windows use the plain format
(`2026`, `2026-H1`, `2026-Q2`, `2026-03`); anniversary windows carry their
cycle start (`a2025-11`, `a2025-11:Q2`), because "the second quarter" is a
different three months depending on when the card was opened. Changing a key
format means a schema version and a migration, never an edit in place.

## Card data

The American Express cards were checked against Amex's benefit terms
pages on 1 November 2026 (see Phase 8 below). The rest of
`data/cards.seed.ts` was checked card by card on 28 October 2026 against
each issuer's own page, cross-checked with The Points Guy and recent

nothing from TPG is copied, and the default valuations are ours, not
TPG's (revised 30 October 2026 to sit closer to the consensus; never
labelled with any publisher's name). Three modelling rules:

- **A credit whose period or amount changes meaningfully gets a new id**
  (`csr-edit`, `gold-resy-50`, `united-tb-10k`), so usage stored under
  the old rules is never read under the new ones. The old rows are
  orphaned, not misread.
- **Benefits without a regular period** (per stay, every four years,
  unlocked by spend) are not credits; they go in the card's `finePrint`,
  which the card drawer shows as "Worth knowing". A credit's `notes` holds
  the one condition most likely to cost someone it.
- **The id `bilt` means Bilt Blue** since the 7 February 2026 relaunch, so
  wallets with the old $0 card keep a card. Obsidian and Palladium are new
  ids. Obsidian assumes dining for its pick-one 3x category.

**A credit's `amount` is per period** (The Edit is `250`, `semiannual`).
The card drawer leads with the year's total from `annualValue` and puts
the per-period amount under it ("$250 twice a year"), so new cards need
nothing extra (owner, 5 November 2026). The Tracker still shows each
period's amount on its slots.

The answer line and the Compare table state the multiplier only ("earns
8x on flights"); cents per dollar is held back by the owner's choice,
though ranking and Compare's winners still use value.

## Calculator and ranking maths

`lib/calculators/engine.ts` holds every number the app states about what a
card is worth: earn rates, caps, break-even, spend value and the "which card"
ranking. Like the reset logic it has no runtime imports (its type imports are
erased), so `node --test` runs its tests directly.

Three rules it exists to enforce:

- **Rank on value, never on the multiplier.** 12x Hilton points at 0.5 cents
  is worth less than 4x Membership Rewards at 1.9. A multiplier-only ranking
  gives the wrong answer confidently, which is worse than no answer.
- **Respect the caps.** Amex Gold earns 4x on groceries to $25,000 a year and
  1x after. Multiplying straight through overstates a $36,000 spender by
  33,000 points. Spend past a cap falls to the card's everything-else rate,
  and a capped everything-else rate falls to 1x.
- **Use the user's valuations, not the defaults.** The Points page says these
  drive every dollar figure in the app, so they have to. Signed-in surfaces
  read `useValuations()` or `useValuation()`; the public landing page has no user and uses
  `DEFAULT_VALUATION_MAP`.

## Card art

Drop a file named after the card id into `public/cards/` and `CardFace` picks
it up. `scripts/build-card-art-manifest.mjs` runs before dev, build and
typecheck, and writes `data/card-art.generated.ts` listing what is actually
there.

The manifest exists because the alternative is requesting
`/cards/<id>.webp` and waiting for a 404 to learn the file is missing, which
paints a blank card for a frame and puts a failed request on the wire for
every card. Cards without art are still common. `onError` still falls
back, for a file removed between a build and a request.

**20 cards have real art** (Platinum, Gold, Sapphire Reserve and Preferred,
Venture X, Blue Business Plus, and Bilt Blue, Obsidian and Palladium; then
all four Delta cards, the four Hilton cards, both Marriott cards, Venture
and VentureOne). On 2 November the owner's newer issuer images replaced
the Delta and Hilton art (Hilton Honors and Delta Blue had shown the wrong
design) and added Aspire, Bevy, Brilliant and Delta Reserve; they show a
sample chip and name and are 480px or more. Gold and Platinum keep their
1536px images: the newer ones were 282px and would be blurry. Converted to WebP with transparent corners flattened onto the
art's own dominant colour. The first seven are 1536x969; the Bilt sources
were only 500px (Obsidian 276px) and are kept at that size, never enlarged.
The owner confirmed permission to use it. 22 more images exist in the
owner's Downloads for cards not in the catalog yet; adding a card means
its earn rates, credits and fee too.

**Next's image optimiser does nothing on Workers** without a Cloudflare
Images binding: `/_next/image` returns the original at every width, so a
320 KB face shipped to every thumbnail. The manifest script therefore cuts
480, 720 and 960 px WebP copies into `public/cards/w/` (gitignored, made at
every build, skipped when current) and `CardFace` passes a `loader` that
picks the smallest copy that covers the requested width. Never enlarge.

**The Wallet's first card paints before the app starts**
(`lib/data/first-card.ts`). Real art made the first card the Wallet's
largest paint, and the wallet can only render after hydration (about 5s on
a throttled phone). A tiny inline script in `<head>` reads which card is
first (a key the store keeps current in both modes, else the stored local
wallet, else the demo seed a new browser is about to get), marks `<html>`,
and preloads that card's smallest cut (480 px: on a throttled phone it
shares the connection with the JavaScript, and the 720 took 3.2s on the
live site); CSS paints it into the skeleton's first slot. The real `<img>`
then lands in the same box. Any change to the
skeleton's first slot must keep its size identical to the real card.

**`CardFace` requires `sizes`**, the width it is really drawn at, measured
(Wallet grid `WALLET_CARD_SIZES`, drawer 280px, Tracker switcher 48px, add
sheet 64px). One blanket value used to send the 960 cut to 48px thumbnails
and the 1536px original to phones; the loader now never goes past the
largest cut. **`public/_headers`** gives static files what `next.config.ts`
cannot, because Cloudflare serves them before the Worker runs: a year's
immutable cache on `/_next/static/*`, a day plus a week's revalidation on
card art and icons, and the security headers. Check with `curl -I`.

`CardFace`'s `priority` means `loading="eager"` plus `fetchPriority="high"`,
not Next's deprecated `priority` prop, and not `preload`, which Next advises
against when the largest image depends on the viewport and the data.

### Client and server boundaries

Plain data exported from a `"use client"` module does not survive into a
server component. The calculator registry is split into
`components/calculators/registry.ts` for exactly this reason; keep data and
client components in separate files when a server page needs the data.

### Hooks

Never write state from an effect to read an external value. Use
`useSyncExternalStore`: `lib/use-media-query.ts` for breakpoints and
`lib/use-stored-flag.ts` for remembered booleans. The lint rule enforces it.

Near-white, never pure white: the page is `bg`, anything raised is
`surface`, demo panels are `panel`. `band` is the warm charcoal of the
landing's privacy section, closing call and footer; it stays dark in both
themes and has its own `band-text`, `band-muted` and `band-line`.

Five pastels: mint, lavender, peach, sky, butter. Each has a `-ink` companion
that is legible on it. In light mode the pastel is the fill and the ink is a
deep hue-matched tone. In dark mode that inverts: the fill is a deep tint of the
surface and the ink carries the colour. A literal 20% alpha pastel on `#151517`
would leave chip text under AA, which is why dark is not just the light value
with opacity.

Every pairing is verified at WCAG AA or better in both themes. Re-verify if you
change one.

A spend category owns one pastel and keeps it on every screen. The mapping
lives in `lib/categories.ts` and nowhere else. Eight categories share five
pastels along family lines; "everything else" is deliberately uncoloured so the
coloured categories keep their meaning.

### Shape

One radius scale, square-shouldered rather than soft: containers
`rounded-widget` (12px), inputs and inner surfaces `rounded-inner` (8px),
buttons, chips and category selectors `rounded-control` (6px), card faces
`rounded-card` (12px, a real card's corner). `rounded-pill` (999px) is only
for tracks, dots, switches and round icon buttons. Nothing picks a radius
outside this scale.

Elevation is one soft layer tinted to the background. Grouping comes from
borders and spacing before it comes from shadow.

### Type

`--font-sans` and `--font-display` are both Geist; `.font-display` sets
weight 500 and -0.03em tracking in `globals.css`. Headlines are two-tone:
the claim in ink, the consequence in `text-muted`. Geist Mono
(`font-mono`) loads only in the marketing layout and is only for
measurements and axis labels. Fonts load through `next/font`, never a
`<link>`.

The logo is `components/shell/wordmark.tsx`: the owner's CREDIT DASH
lettering as a CSS mask of `public/brand/wordmark.png` (black on
transparency, cut from the owner's artwork), painted with `currentColor`
so it follows the theme. Size it by height.

Instrument Serif and Fraunces are banned: they are the two most recognisable
generated-site display serifs. (This is a deliberate change from
`creditdash-plan.md` section 3.4, agreed with the owner.)

Numbers are tabular by default so balances line up in a column.

### Motion

Curves and durations are tokens. Pick by element type:

| Element | Duration | Curve |
|---|---|---|
| Button press | `--cd-dur-press` 140ms | `ease-out` |
| Hover, colour change | `--cd-dur-hover` 180ms | `ease-out` |
| Tooltip, small popover | `--cd-dur-pop` 200ms | `ease-out` |
| Dropdown, select | `--cd-dur-menu` 220ms | `ease-out` |
| Drawer, calculator panel | `--cd-dur-panel` 280ms | `ease-drawer` |

Rules:

- **Never `ease-in` on UI.** It delays the first frame, which is the moment the
  user is watching most closely, so it reads as sluggish.
- **Never `transition: all`.** Name the properties.
- **Animate only `transform` and `opacity`.** Never `width`, `height`, `top`,
  `left`.
- **Never animate from `scale(0)`.** Start at `scale(0.95)` with `opacity: 0`.
  Nothing in the real world appears from nothing.
- **Every pressable element gets `active:scale-[0.97]`.**
- **Popovers scale from their trigger**, not from centre. Modals are the
  exception and stay centred.
- **Motion's `x`/`y` shorthand props are not hardware accelerated.** They run on
  the main thread and drop frames under load. Use a full `transform` string.
- **Prefer CSS transitions over keyframes** for anything that can be retriggered
  rapidly. Transitions retarget mid-flight; keyframes restart from zero.
- **Never `window.addEventListener('scroll')`.** Use Motion's `useScroll`, an
  `IntersectionObserver`, or CSS scroll-driven animation.
- **Nothing routine runs over 300ms.**
- Import from `motion/react`, not `framer-motion`.
- Isolate motion in `'use client'` leaf components. Layouts stay server
  components.

`prefers-reduced-motion` is handled globally in `globals.css`. Reduced motion
means gentler motion, not none: opacity and colour still carry meaning,
movement does not. Anything with its own JS-driven motion must also check
`useReducedMotion()`.

## Writing the interface

### Rules that produce a generated-looking site, so are banned

- **Zero em dashes (`—`) and zero en dashes (`–`) in any visible string.**
  Headlines, labels, body, buttons, captions, alt text, error messages. Use a
  comma, a period, parentheses, or a plain hyphen. This is the single most
  recognisable tell.
- No purple or blue gradient hero, no gradient text, no glowing blobs.
- No filler verbs: "Unlock the power of", "Elevate your", "Seamless",
  "Revolutionize", "Next-gen".
- No emoji as icons. Use Phosphor glyphs.
- No three identical feature cards in a row with an icon on top.
- No uppercase wide-tracking eyebrow label above every section. At most one per
  three sections.
- No section numbering (`01 / INDEX`, `002 · Capabilities`).
- No scroll cues ("Scroll to explore").
- No decorative status dots unless the dot means a real state.
- No fake product screenshots built from `<div>`s.
- No placeholder text. Sample data is specific and real-feeling: actual card
  names, real amounts, real dates. Never "Lorem ipsum" or "$XX.XX".
- No generic names or brands ("John Doe", "Acme").
- Do not centre everything. Layouts are deliberate and slightly asymmetric.
- No default shadcn look. Restyle every component to the tokens.

### Copy

Plain, active, sentence case. Name things the way a user would. A button says
what happens: "Save changes", not "Submit". The same action keeps the same name
through a whole flow, so a "Publish" button produces a "Published" toast.

Errors explain what went wrong and how to fix it, without apologising and
without being vague. An empty screen is an invitation to act, not a mood.

Re-read every visible string before calling a screen done. If a phrase is cute
but does not quite make sense, replace it with a plain one.

### Quality floor

Every screen, every time:

- Works at 375px and at desktop width, with no horizontal scroll. Measure it
  (`scrollWidth - clientWidth`) rather than eyeballing; 35px of drift is
  invisible in a screenshot and real on a phone.
- **`sr-only` inside a horizontal scroller needs a positioned ancestor.** It
  is `position: absolute`, so without one its containing block is `<body>`,
  it lands at the scroller's unclipped coordinates, and it widens the whole
  page. `overflow: hidden` does not clip it, which is why this hides well.
  Add `relative` to the cell or wrapper.
- **A flex item will not shrink below its content unless you let it.** Five
  tab bar items with `flex-1` needed 410px on a 375px phone. `min-w-0` plus
  a truncating label is the fix.
- Every interactive element has hover, press, focus and disabled states.
- Focus is visible and never removed. The treatment is global in `globals.css`.
- Light and dark both checked. Never ship a screen seen in one mode only.
- Empty, loading and error states exist. Loading is a skeleton shaped like the
  real content, not a spinner.
- One clear focal point per screen, with type size and weight doing the work.

## Data and privacy

- Never store or request card numbers, expiry dates, CVVs or bank logins. There
  is no field for them anywhere.
- All data access goes through `lib/data/`. Pages never touch storage directly.
  Phase 6 swaps browser storage for Supabase by changing that layer only.
- Every premium check goes through one `hasFeature` helper against one limits
  config, so a feature can move between Free and Premium in one edit.
- Secrets live in environment variables and never in the repo. `.env.example`
  carries names only.
